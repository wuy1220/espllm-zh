# 2026 年 10 月：在这个 1 MB / 40 KB 的盒子里，还有什么值得试

两份调研合在一份里：

1. 外部新方法里，哪些落在我们的约束内（**第一部分**）
2. 再训一个中文角色 chatbot 的可行性（**第二部分**）

标注：**[实测]** = 本机/板上跑过；**[估计]** = 按现有预算脚本或论文数字推算；**[外部]** = 论文/仓库自报，未复现。

---

## 第一部分：外部新方法盘点

### 0. 先把判据钉死

外面绝大多数"新方法"默认你有 GB 级显存和 TB 级带宽。我们只有三条真约束：

| 约束 | 数值 | 后果 |
|---|---|---|
| 可寻址 flash（`irom0_0_seg`） | 1,044,464 B，已用 1,002,475 | **模型封顶 ~2.5M 参数**（4L/48E 就是 99.6%） |
| arena（DRAM） | 40,960 B，5L 需 39,360 | **深度 × 窗口封顶**，5L@104 就是天花板（6L 要 46,432） |
| 每 token 权重流量 | ~70–170 KB | 延迟 ≈ 流量 / 有效带宽，**不是 MAC 数** |

凡是"压缩率更高 / 吞吐更高"但需要更多 DRAM、更多代码区、或需要浮点 SIMD 的方法，在这里一律为负收益。下面按"落在约束内"筛。

### 1. 语料：值得试的两条，都不是"再加数据"

**1.1 结构化改写（FinePhrase，HF 2026-03）[外部]**

把网页/文档改写成四种结构：**FAQ / 表格 / 数学题 / 教程**，而不是让大模型"重新写一遍"。
333 次训练对照、1T token 的结论里，对我们最有用的两条是：

- **改写模型超过 1B 就没有额外收益**（Gemma 3 1B 的数学 prompt 15.31 > 27B 的 14.76）。
  也就是说这个活本地跑得动。
- 结构化格式**一致优于** curated web baseline；提升集中在阅读理解与数学，常识推理没有。

对我们意味着什么：我们缺的从来不是 token 量（2.2M 窗口 ≈ 287M token/epoch，早已过剩），
而是**形状**。现有三种 prompt 全是"文本 → 故事散文"，`summary → 第一句` 本身是低信息量映射，
模型学到的正是"忽略输入吐开头"（短输入 pairwise KL 0.017）。把 `Summary` 改写成
`FAQ`（"这个故事讲了谁？"→ 一句话）和 `教程`（"用这些词写故事的第一步是什么？"）
是**在现有语料上就能做**的结构化改写，不需要新数据集。

**1.2 课程式合成 + 知识图谱（Sutra-10B）[外部]**

1,942 个概念 × 9 领域，按先修关系排序生成；50-30-20 混合（教科书 / 过滤网页 / 教育网页）。
对我们的价值不在规模，在**"按主题分桶 + 每桶覆盖多少问法"这个数据设计范式**——
这正好是角色 chatbot 需要的东西（见第二部分）。

**1.3 模板合成对话（GuppyLM）[外部]** —— 第二部分详述，这是中文角色模型的主力。

**不要做的**（已被我们自己的实测否掉，别翻案）：

- 再混意图语料：四轮全否，6% 就能把 P(Once) 打下来但题材被罐头污染，文本塌缩。
- 再找外部对话语料：SODA 只有 0.3% 能装进窗口，截短 +1.8 nats，结构性不匹配。
- 用更大模型合成海量数据：2M 参数吃不下，FinePhrase 那套是给 1.2B student 用的。

### 2. 架构：三条，按性价比排

**2.1 跨层共享 KV（CLA / YOCO）—— 直接打 arena 墙 [估计]**

这是本轮唯一"新发现且命中要害"的架构项。我们现在的死结是：
`ARENA_NEED = 4,000 + 7,072·N_LAYER`，5 层已 39,360，6 层要 46,432，**超 40,960**。
所以"同预算给深度"这条线卡在 5 层。

CLA 让相邻两层共享同一份 K/V（只各自保留 Q），KV 直接减半：
5 层从 21,760 → ~11,000，6 层从 26,112 → ~13,000。**arena 立刻不再是约束**，
窗口和深度可以同时要。

代价：质量损失（论文报 ~1% 级别），以及 `ctx_slide`/`ctx_renumber` 要对"一份 KV、两层共用"
做引用计数——实现上不难，但**必须先证明质量不掉**。PC 上改 `main.py` 加 layer-pair K/V 共享，
固定验证集跑一次 CE 就知道，半天工作量。**如果 CE 不涨超过 0.02，就上。**

**2.2 共享专家（shared expert）—— MobileMoE 的结论，我们没试过 [估计]**

MobileMoE（Meta，2026-05）在 0.3–0.9B active 区间的结论是：on-device 最优是
**中等稀疏 + 细粒度专家 + 共享专家**，共享专家承载通用知识、路由专家做专精。
我们 5L/32E 全是路由专家，没有共享专家。

成本极低：1 个共享专家 = 2,946 B/层 × 5 = **14,730 B flash**（余量 41,989 够），
每 token 多读一个专家 ≈ +2.9 KB 流量（<2% 延迟）。可做。

但要说清楚：**我们的 A/B 与 MobileMoE 不矛盾**。他们内存是 GB 级，容量不是约束；
我们 1 MB 封顶，同预算下深度 > 专家（4L/40E → 5L/32E，CE −0.0624，五族同向）。
共享专家是在"专家数已饱和（32 附近）"之后，唯一还能提升专家利用率的结构改动。

**2.3 窗口 104 → 64 —— 已排期，最简单的一步 [实测支持]**

32/64/104/128 的 rep8 与 distinct-4 全在 0.93~0.99，**质量无差别**；省 13.6 KB arena、
注意力快 ~20%。省下的正好够 6L/32E（6×64 格 ≈ 30.1 KB）。

**不做**：Mamba-2 混合（Nemotron 3 路线）。它确实能消掉窗口限制（O(1) 状态），
但在 ESP8266 上要把 exp / scan 做成定点，等于重写全部 kernel，换来的只是"窗口无限"——
而我们窗口 104 已经够用，且滑窗开销只占 1.6%（954 ms / 59.8 s）。**收益不抵工程量。**

### 3. 训练：**这个方向已经封顶了，不要再查**

**[2026-10-20 补测，实测] 原生 ternary 训练早就已经在跑了。**
写这份文档时的第一版判断是"我们做的是 PTQ，原生 QAT 是最大未试杠杆"——**错的**。
`main.py:744` 的 `BitLinear` 就是训练路径本身：absmean 分组量化到 {−1,0,+1}、
per-token int8 absmax 激活、STE，`Transformer` 里 qkv / proj / MLP 三路 / lm_head
全部是 `BitLinear`。`convert_to_bitlinear()` 只是导出时把同一套量化的权重冻结成 int8+fp16。

于是真正没量过的问题变成两个，`eval_qat_ablation.py` 一次跑完
（`model_5l32e.pt.best`，固定验证集 60 batch × 128 × 128 = 983,040 token，四臂共用同一批数据）：

| 臂 | 权重 | 激活 | val CE | 相对臂 0 |
|---|---|---|---|---|
| 0 | ternary | int8 | **2.0627** | — |
| 1 | ternary | **fp32** | 2.0626 | −0.0000 ± 0.0001 |
| 2 | fp32 | int8 | 7.4874 | +5.4248 |
| 3 | fp32 | fp32 | 7.4829 | +5.4203 |

两条结论，都很干净：

1. **激活的 int8 钳位是免费的，代价 0.0001 nats。** 板上跑的是 fp32 激活
   （`src/main.cpp` 里 `g_x` / `g_xnorm` / `g_qkv_out` 全是 `float`），而训练时假装
   它是 int8。我原本以为这中间有免费收益——**没有**，127 级 absmax 对这个模型完全不紧。
   所以这条"误配"不用修，修了也不会涨分。
2. **fp32 权重直接崩到 CE 7.49**，那是 QAT 检查点里的"潜在权重"，本来就不可用
   （项目里早有这条结论）。臂 2/3 的作用不是量 PTQ 代价，而是**确认没有 PTQ 阶段的
   损失可以回收**——这个模型从来没有"先用 fp32 训好、再压坏"的历史。

**所以：训练侧的能量已经全部用掉了。** 剩下的只有架构（深度 / KV 共享 / 共享专家）
和语料。不要再在"QAT / PTQ / 比特分配"上花时间。

### 4. 推理优化：大部分与我们无关

| 方法 | 结论 | 理由 |
|---|---|---|
| KV 自适应量化（CVPR 2026）、TurboQuant、TriAttention | **不做** | 我们 KV 只 21,720 B，不是瓶颈；窗口大小就是我们的 eviction 旋钮，而且比任何打分策略都便宜 |
| 投机解码（draft model） | **不做** | 6.7 tok/s 且可切块；MCU 上加一个 draft 模型 + 校验逻辑，代码区和复杂度都不划算 |
| 2-bit 输出头打包 | **已上线** | 26.0 → 15.6 ms，省 95 KB，logits 逐位不变 |
| prefill 跳过 head | **已上线** | 88 → 83 ms/prompt token |
| 块稀疏注意力（NSA / AsyncTLS） | **不做** | 都是 >1B 的吞吐技巧，我们在 104 格全扫 |

**唯一值得做的推理项：把权重搬进 LittleFS（3.1 MB）**——

现在 `eagle.flash.4m3m.ld` 给了 spiffs 3,121,152 B，几乎全空着。把模型放 FS 意味着
**容量约束从 1 MB 变成 3.1 MB**，能装 2.2 倍大的模型、或者英文/中文两个模型共存。
已有的小规模实测是"每层从 FS 拉一个专家，4 层只 +1.74 ms/token"，但**整模型流式从未端到端验证**。
这是路线 B 的最大未知数，应该先花 30 分钟做一个 spike：从 FS mmap 顺序读 600 KB，
量实际 MB/s 和每 token 增量。

### 5. 压缩：只剩"分层混合精度"

2-bit head 已上线；ternary 权重已裁决；低秩/SVD 已否决（r=48 +0.84）。

唯一没试的是**按层分配比特**：第一层和最后一层对质量更敏感，给 2.4 bit（或保留 fp16 scale 更细），
中间层压到 1.58 bit。我们现在的 packing 是全局统一的，没有 per-layer 位宽通道。
收益不确定（估 5~15 KB 换 0.02 nats 以内），优先级低于 3.1。

### 6. 排序（收益 × 成本）

| # | 事项 | 预期收益 | 成本 | 风险 |
|---|---|---|---|---|
| 1 | **原生 ternary 训练** | CE −0.1~0.3 [估计]，固件零改 | 100 行 + 5.4 h | 小模型收益可能缩水 |
| 2 | **窗口 104→64** | 解锁 6L/32E，注意力快 20% | 半天 | 无（质量已证） |
| 3 | **跨层共享 KV** | arena 墙消失，深度/窗口脱钩 | 半天 PC 验证 + 1 天固件 | 质量掉多少未知 |
| 4 | **共享专家** | 专家利用率 | 2 h + 6 h 训练 | 小 |
| 5 | **权重放 FS** | 容量 1 MB → 3.1 MB | 先 spike，再 2–3 天 | 流式速度未验证 |
| 6 | **结构化改写语料** | 治"不听输入" | 1–2 天 | 需固定验证集判读 |
| 7 | 分层混合精度 | 5~15 KB | 2 天 | 收益小 |

## 第二部分：中文角色 chatbot 可行性

### 结论先说

**可行，但必须换目标。** 目标不是"会聊天的助手"，而是 **GuppyLM 那种封闭域角色**：
20~30 个话题、每轮 20~30 字、人设烤进权重、不用 system prompt。

三条外部证据和一条我们自己的证据指向同一个结论：

- **GuppyLM** [外部]：8.7M 参数、6 层 dim 384、词表 4096、**128 token 窗口**，
  6 万条合成对话、60 个话题，Colab T4 训 5 分钟，就能稳定扮演一条鱼。
  它的关键判断是：**"9M 参数的模型无法条件跟随指令，人设必须烤进权重"**，
  顺便省掉每轮 ~60 token 的 system prompt。
- **某人做的中文 ESP32 项目** [外部]：7.83M 参数、**输入词表 6400 / 输出词表 4096**、
  5,920 条问答覆盖 **55 条原子事实**，真板跑通。
- **沐雪 / HundredCV-Chat / DuLeMon** [外部]：中文角色对话数据是有的，
  但规模都在千条级（沐雪 3,541 条），必须自己合成扩量。
- **我们自己的诊断** [实测]：模型在 `continue` 模板下**确实读输入**（名字命中 73%，
  换内容 pairwise KL 0.86），在 `summary` 模板下几乎不读（KL 0.017）。
  **差别不在容量，在语料形状。** 角色 chatbot 恰好是"短输入 + 短回复"——
  如果不换语料形状，它会 100% 落在我们失败的那个区域里。

### 硬约束逐条核

| 约束 | 现状 | 中文模型 | 判断 |
|---|---|---|---|
| 词表 | 2048（BPE） | 汉字需要单独设计 | **可行，见下** |
| 序列长度 | 104 | 24 字 prompt + 40 字回复 = 64 | ✅ 富余 |
| 每 token 延迟 | 97~150 ms | 同 token 数同延迟 | 30 字回复 3~4.5 s |
| 训练时间 | 30k 步 ≈ 5.4 h | 同 | ✅ |
| Flash | 1,002,475 / 1,044,464 | 词表不变则不变 | ✅ 路线 A |

### 词表：这是唯一真正的硬问题

汉字覆盖率 [外部]：**1000 字 92%，2000 字 98%+，3000 字 99%+**。
TinyStories-Zh-2M 全量只有 **2,492 个不同汉字**（199M 字），
比通用书面语更集中——因为它是儿童故事。

三套方案，成本都算清了（每个词表条目 = tok_emb int8 64 B + tok scale 4 B
+ head 2-bit 16 B + head scale 4 B = **88 B**）：

| 方案 | 词表 | 覆盖率 | Flash 增量 | 结论 |
|---|---|---|---|---|
| A1 | 2048 = 2000 汉字 + 48 控制 | ~98%（域内接近 100%） | **0** | **推荐先做** |
| A2 | 2560 = 2500 汉字 + 60 控制 | ~99.3% | +45,056 B（超余量 3 KB） | 要减 1 个专家 |
| B | 3000 = 2900 汉字 + 100 控制 | ~99.4% | +83,776 B | 必须降一层 |

A1 的关键操作是**语料侧裁剪**：把训练语料里出现 2000 字以外的句子丢掉或替换。
对封闭域角色对话，被丢掉的量会很小（角色本身不会说生僻字），
代价是"用户输入里的生僻字认不出"——但输入侧可以走规则层兜底。

**附带好处：字符级分词顺手修掉了一个老 bug。** 现在 2048 BPE 里有 128 个 token 的
`decode([i])` 是 U+FFFD（多字节汉字被按字节切开），单独生成就吐 `â€` 乱码。
字符级编码**按定义**不会产生这种碎片，乱码问题从结构上消失。

C 端实现也比现在简单：encode = UTF-8 解码 → 二分查 2000 条排序表；decode = 直接查表。
不需要 merges，不需要最长匹配。

### 两条路线

**路线 A：复用现役固件（1~2 天）**

- 架构不动：5L/32E、dim 64、vocab 2048、窗口 104。**固件只改 tokenizer 表和意图规则。**
- 2.17M 参数（激活 0.26M）。GuppyLM 是 8.7M dense —— 我们小 4 倍，
  所以**话题数要压到 15~20，回复 20~25 字**。
- 用途：**先回答"这条路走不走得通"**，1~2 天出结论，零固件风险。

**路线 B：容量升级（3~5 天，需 FS 支持）**

- `dim 64 → 128`、`n_head 2 → 4`（**head_dim 保持 32，KV arena 一点不变**）、`mlp_hidden 64 → 128`
- 参数 **8.35M**，正好 GuppyLM 量级；权重 **≈2.8 MB**，必须放 LittleFS（3.1 MB 可用）
- 延迟 [估计] 250~400 ms/token → 30 字回复 8~12 s。符合"质量优先，速度让步"。
- 已经有有利条件：`main.cpp` 里 `N_EMBD` 被引用 40 次、没有硬编码 64 的维度假设，
  converter 从 checkpoint 自动推导 `n_embd/n_head`，所以**架构层大概率"只是换个头文件"**。
  真正的新工作只有两件：① FS 权重加载器 ② converter 支持 hpp→FS 分片。
- 注意：往 FS 写 2.8 MB 在 54 KB/s 下要 **~52 分钟**，一次性，但调试循环会很慢。

**顺序建议：先 A 后 B。** A 产出的词表、语料、评估口径 B 全部复用，A 失败则 B 不用做。

### 语料配方

角色卡（示例）：名字、身份、口头禅、说话长度上限、知识边界（不知道就说不知道）。

三类来源，按可靠性排：

1. **模板合成（主力，零依赖）**——GuppyLM 的做法：60 个话题 × 30 个对象 × 17 种活动，
   约 60 个模板组合出 ~1.6 万条唯一输出。我们的额度：**20 个话题 × 40 个问法 × 30 个回复
   = 2.4 万条**，纯 Python 生成，不花钱、不依赖大模型、完全可控。
2. **大模型改写（补自然度）**——把模板句改写成更口语的说法，用 7B 级模型即可
   （FinePhrase 的结论：超过 1B 就没额外收益）。
3. **TinyStories-Zh 打底（可选）**——199M 字儿童故事只用来撑语言能力，
   混比 **≤ 20%**，且必须按"族"分开评估，否则会重演意图语料那次的文本塌缩。

prompt 格式（必须和训练逐字节一致，这是我们踩过的坑）：

```
用户：<用户这一句>
<角色名>：<回复，≤25 字，句号结尾>
```

**不加 system prompt。** 人设靠权重，不靠前缀——这既是 GuppyLM 的结论，
也是我们自己的诊断：短输入本来就 OOD，再加一段 system prompt 只会更长更 OOD。

### 验收口径（可测量，不靠"感觉像不像"）

| 指标 | 工具 | 现状（英文） | 目标 |
|---|---|---|---|
| 短输入是否被读取 | `probe_first_shape.py` pairwise 归一化 KL | 0.017 | **> 0.5** |
| 人设词命中 | 采样统计 | — | > 80% |
| 首 token 分布熵 | 采样统计 | ~4.2 nats | < 2.5 nats |
| 平均回复长度 | 采样统计 | 20~40 tok | 20~25 字 |
| 收尾率 | 采样统计 | 97% | > 90% |
| 乱码 | 字符级 tokenizer | 1~2% | **0（结构性消除）** |

第一条是**生死线**：如果短输入 KL 还是 0.02，说明模型依旧在"随便挑个开头"，
那这个机器人只是另一个故事机，不如不发布。

### 风险

1. **2.17M 装不下角色一致性**——GuppyLM 是 8.7M。对策：A 阶段先把话题数降到 15，
   不行就走 B。
2. **中文没有"OOV 词表"口径**——英文用 TinyStories 11,745 词表算 OOV，
   中文要重新定义（2000 字表外的字占比），且语料已裁剪到 0，这条指标会失效。
   替代：用"非法字序列 / 重复 n-gram / 平均句长"三条。
3. **路线 B 的 FS 流式速度未验证**——最大未知数，先做 spike。

## 一句话版本

- **方法侧**：真正没试过、又不需要动固件的大杠杆只有一个——**原生 ternary 训练（QAT）**。

  换成"对话对"**——这是我们已经量化过的那个 0.017 的根因。
