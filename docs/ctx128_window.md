# 上下文窗口 64 → 104：按"质量优先"做的取舍

结论先说：窗口从 64 提到 **104**，模型在 129 宽窗口上微调了 2400 步。
同口径验证损失 2.6943 → **2.1665**（ppl 14.8 → **8.7**），chat 子集 2.7487 → **1.8538**
（ppl 15.6 → **6.4**）。之前那个 40.8 秒的回复现在 7.2 秒，而且输出更长。

## 为什么不能"直接把窗口调大"

固件原本把窗口硬钉在 `model_block_size=64`，因为训练只见过 64 个位置。要把窗口
放大，先得回答两个独立的问题，它们经常被当成一个问题：

**问题一：位置编码能不能外推？能，而且是免费的。**

`rope_cos/rope_sin` 只有 64 行。把同一批 64 token 的位置整体平移 +16 / +32 / +64 / +128，
损失变化 **≤ 0.0003 nats**（`ctx_rope_shift.py`）：

| 位置 | val | 相对基线 |
|---|---|---|
| 0..63 | 2.5876 | — |
| 16..79 | 2.5874 | −0.0002 |
| 64..127 | 2.5874 | −0.0003 |
| 128..191 | 2.5874 | −0.0002 |

RoPE 只吃相对距离，绝对偏移它根本不关心。所以"表只有 64 行"从来不是限制。

**问题二：注意力能不能在 128 个 key 上正常分配？不能。**

用 TinyStories 的连续 129 token 序列，把**同样 64 个目标 token** 用两种方式打分
（`ctx_len_eval.py`）：

| 目标 token 的上下文 | val |
|---|---|
| 无前缀（独立 64 窗口） | 2.5781 |
| 有 64 token 前缀（位置 64..127） | 2.9605 |

逐位置看更清楚（128 窗口内）：

```
位置   0-15  16-31  32-47  48-63  64-79  80-95  96-111  112-127
val   2.72   2.56   2.58   2.53   2.48   2.62   3.20    3.55
```

64-79 是**最好**的一段（2.48，比无前缀还好），说明多出来的上下文确实有用；
但 96 之后迅速崩掉。**模型能用的历史大约 80 个 key**，超过就退化。

结论：窗口可以扩，但必须微调，不能靠外推。

## 训练怎么做的

**语料**：`build_long_corpus.py` 重建 129 宽语料（`dataset_mixed3.txt`，866 MB as int16，
3,356,672 窗口）。故事半边从 flat 流按 129 重新切片（1,356,722 窗口），
chat 半边 65 宽的 199,995 条原样保留 ×10，由训练器 pad 到 129 并掩码。

没有复用 `mix_corpora.py` 是因为它把每个窗口先物化成 Python list，4.3 亿个 int
要 15 GB；而且它的 `len(w) == win or m > 0` 过滤会在 block=128 时把 65 宽的 chat
窗口**全部丢掉**，语料里一个 chat 样本都不剩却不会报错。顺手给它加了 `--keep-short`。

**warm start**：`load_checkpoint` 原先会因为 `block_size: ckpt=64 vs cfg=128` 直接拒绝。
但 rope 表是 `block_size` 的纯函数、不是学习参数，所以把它从硬性不匹配里放出来：
block_size 差异只打印一行提示并重建 rope，其余字段照旧拒绝。

**训练**：从 `model_mixed2_init.pt` 热启动，batch 32 × block 128，lr 2e-3 余弦，
8000 步上限，**2400 步早停**（val 2.9946）。约 0.8 s/步。

## 结果

同口径（`eval_128_ab.py` / `eval_split.py`，8 个 batch × 32 窗口，纯交叉熵，
无 label smoothing、无 aux）：

| | 128 宽混合 val | chat 子集 | 
|---|---|---|
| 旧模型（64 训练） | 2.6943 (ppl 14.80) | 2.7487 (ppl 15.62) |
| **新模型（128 训练）** | **2.1665 (ppl 8.73)** | **1.8538 (ppl 6.38)** |

旧模型在 chat 子集上的数字是它自己的自然窗口（65 宽），仍然差 0.9 nats ——
这一项不是"窗口变长带来的"，是微调本身把 chat 分布也学好了。

## 固件：窗口为什么是 104 而不是 128

arena 是静态 40 KB，KV cache 每位置 272 B（K+V 各 32 维 int8 + 两个 fp16 scale），
固定缓冲 10752 B（其中 2048 float logits 占 8192）。解方程：

```
276 * N + 10752 <= 40960  ->  N <= 109
```

取 **104**，留 1.5 KB 余量。同时加了编译期 `static_assert(ARENA_NEED <= ARENA_SIZE)`，
以后再导出更大 block_size 会直接编译失败，而不是运行时拿到空指针后无限重启。

Flash 761 KB（72.9%），RAM 73,912 B（90.2%），free heap 6552 B —— 与改动前基本一致
（rope 表 +8 KB flash，其余不变）。

## 板上实测

| 提示词 | 改动前 | 改动后 |
|---|---|---|
| she opened the box and | 40842 ms / 60 tok（680 ms/tok） | **7175 ms / 80 tok（89.7 ms/tok）** |
| the old lighthouse keeper found a | 4776 ms / ~60 tok | 7397 ms / 80 tok（92.5 ms/tok） |
| once upon a time there was a little girl | 4575 ms / ~60 tok | 8320 ms / 80 tok（104 ms/tok） |

之前 680 ms/token 的来源是 `ctx_push()`：窗口一满就 memmove 掉最老一个 token 并把
`ctx_pos` 归零，于是下一个 token 要把整个 63 token 前缀重新前向一遍。104 窗口下
prompt(~12) + 80 = 92 < 104，这条路径根本不会触发。

另外在 prefill 之前加了一道保险：如果 prompt 本身就快把窗口填满，先从头砍掉多余的
token（此时 `ctx_pos` 还是 0，没有 KV 要作废，所以是免费的），保证整段回复都有位置。
214 字符的长输入实测 8923 ms / 80 tok，没有尖峰。

## 两个预算

- **story 80 token**：`MAX_GEN_TOKENS`
- **chat 32 token**：`CHAT_MAX_TOKENS`

chat 需要单独的上限，因为模型并不总会吐出那个用来结束回复的换行。

顺便记录一个**试过又回退**的改动：把停止条件改成"换行且前一个可见字符是句末标点"，
本意是避免 "...a little girl at\n" 这种半句截断。实测反而更差 —— 模型在 80 token 内
很少真正收句，于是每条 chat 回复都变成 7.4 秒的漫谈且仍然半句结束。回退成
"首个换行即结束 + 32 token 上限"，回复回到 1.5 秒 / 16-18 token。

## 还没解决的

chat 路径对任意问题都以 "Once upon a time..." 开头。这不是本次改动引入的
（旧模型同样答成故事），根源在 `dataset_chat.txt`：它是 TinyStories-Instruct 的
摘要条件记录，问题与答案本身不匹配（"A king and queen find a beautiful crown"
对应的答案是"山脚下的小村庄"）。模型学到的只是"看到 User: 就写个故事"。
要真正改善问答，得重做 instruct 数据，那是另一个项目。
