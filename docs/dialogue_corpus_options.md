# 对话语料：有什么合适的，实测到哪一步

问题不是"哪个对话数据集质量高"，而是"哪个能被我这个 117 万参数、词表 2048、
窗口 104 的模型吃下去"。这两个问题的答案差别很大。

所有标 **[实测]** 的数字都在本机跑过；标 **[估计]** 的是数据集卡片/规模推算，没跑。

---

## 结论

1. **公开对话语料里，没有一个是"直接换上去就行"的。** 最像的 SODA，只有 **0.3%**
   的样本能装进我们的窗口，截短后代价仍是 **+1.8 nats**。
2. **最该用的是我们自己语料里被丢掉的东西**：`Features: Dialogue` 标签覆盖
   **71.9%** 的记录（2 万条抽样），平均每篇 5.1 条引号对话、每条中位 7 个词。
   折算全量约 570 万条可用回复，**词表、语域、许可全部零成本**。
3. **补问答要做"抽取式"，不要做"总结式"。** 从故事里抽一句话当答案，代价
   **+0.24 nats**（2.40 → 2.64）；让模型输出摘要，代价 **+1.11 nats**，而且答案
   中位 40 token —— 超出固件 32 token 预算，教出来的形状我们根本采不出来。
4. **事实题不该靠语料解决。** 见第五节。

---

## 一、先划清楚"缺什么"

现在的 `dataset_mixed4` 里 chat 占 41%，已经是"问题→回答"的形状，但三种 prompt
都是围绕"讲故事"的。板上实测：句末收尾 80%、Once upon 开场 3%，**这两个病灶已经
修好**。剩下的唯一问题是模型把事实题也答成故事。

这不是数据量问题。HF 上那批微模型里最强的 Nano 用了 300 亿 token，一样答不了
`what is a cloud`（它会把问题续写成维基腔的段落）。117 万参数装不下世界知识。

所以语料该学的目标是**"怎么接话"**，不是"什么是真的"。

---

## 二、外部语料实测

测量口径和训练完全一致：只对答案 token 算损失（prompt 用 `-100` 掩掉），
一问一答各自成一个窗口，prompt 超过 96 token 的样本直接判为"装不下"。

参照点：**control = 2.40**（用现有语料重新拼一遍，验证口径无误）。

| 语料 | 能装进窗口 | 答案 CE **[实测]** | ppl | 答案长度中位 | 判断 |
|---|---|---|---|---|---|
| **control（现有语料）** | 98% | **2.396** | 11.0 | 20 tok | 参照 |
| **story 内抽取问答（who/what）** | 100% | **2.643** | 14.1 | 20 tok | **+0.24，几乎免费** |
| **故事里的引号对话** | 100% | 3.334 | 28.1 | 15 tok | 提取太粗糙（见 §3），真实构建会更好 |
| **summary 当答案** | 100% | 3.512 | 33.5 | 40 tok | +1.11 且超预算 |
| **让模型说出给定词表** | 100% | 4.664 | 106 | 10 tok | **信息论上不可学**，见 §5 |
| **SODA（allenai/soda）** | **0.3%** | 4.230 | 68.7 | 17 tok | **不可用** |

### SODA 为什么不可用（这是最有信息量的一条）

`allenai/soda` 是社交对话里质量最好的一批之一（CC-BY-4.0，14.6 万条）。实测它的
prompt 长度分布：

```
prompt tokens   median 253   p10 164   p90 408   max 963
prompt <= 96 tok（我们的训练上限）   11/3397 = 0.3%
answer tokens   median 19    p90 49    answer <= 32 tok: 76.4%
```

**答案长度完全合适，上下文长度完全爆炸。** 它的每条对话都挂在一段场景叙述 +
4~8 轮对话后面，中位 253 token，是窗口的 2.4 倍。我们把上文强行截到最后三句
再测，答案 CE 仍是 **4.23**（+1.8 nats）—— 因为截断把衔接逻辑也一起砍掉了。

结论：SODA 这类"长场景 + 多轮"的语料，对我们不是"贵一点"，是**结构性不匹配**。

### 其余候选为什么没进表

| 数据集 | 为什么没测 |
|---|---|
| `smoltalk`（GPT-4o 蒸馏，2.2M 对话） | 分片 223 MB，答案普遍 100+ token，教出来的形状用不上；先不进 |
| `daily_dialog` | 唯一语域接近的（13k 人工对话、日常话题），但仓库只给加载脚本，没有 parquet，本机镜像限流下没取到；**[估计]** 约 140 万 token，太小，只能当 5% 的配菜 |
| `empathetic_dialogues` / `persona_chat` | 同样只有脚本；且带 `_comma_` 之类的转义残留，清洗成本高于收益 |
| OpenAssistant / Dolly / Alpaca | 世界知识与长答案，与我们差 2 nats 以上（FineWeb 实测 5.20、Cosmopedia 6.09） |
| Simple English Wikipedia | 事实性语料，且本机 wikipedia 域被代理挡死（502），取不到 |

## 三、最大的一笔未用资产：`Features: Dialogue`

TinyStories-Instruct 的每条记录都带 `Features` 字段，我们一直只用 `Words` 和
`Summary`，把 `Features` 扔了。2 万条抽样：

```
records scanned 20000, tagged Dialogue 14375 (71.9%)
quoted turns per story: median 4, mean 5.1
words per quoted turn:  median 7, p90 19
usable prompt/reply pairs: 12598 / 14375（剩下的没有引号）
```

折算到 134 万条全量记录：**约 570 万条引号对话**，每条中位 7 个词（约 10 token），
天然落在 32 token 预算内，且全部是模型已经会的词。这是零成本的对话语料。

我抽了 400 条测 CE，得到 3.334 —— 但**这个数字不该当成代价**：我的提取方式
太粗糙（只拿最后一句叙述当 prompt，会出现 `User: " Lily replied, "I found it...`
这种悬空引号）。真正构建时应该给前 2~3 句叙述 + 前 1~2 轮对话，CE 会明显低于 3.33。
**下一步该做的是认真构建一版再测，而不是照这个数判死。**

## 四、按代价排序的选项

| 选项 | 供给量 | 增量代价 | 建议 |
|---|---|---|---|
| **A. 抽取式问答**（"Who is in the story?" → 故事第一句） | 每篇 1~3 条，全量百万级 | **+0.24 nats** | **先做这个** |
| **B. 引号对话重排**（72% 记录，570 万条） | 570 万条 | 待测（粗测 3.33 偏高，是提取问题） | **第二步，认真构建再测** |
| C. DailyDialog 当配菜（5~10%） | ~140 万 token | 未知 | 想试语域再试，别指望它带来知识 |
| D. summary 当答案 | 百万级 | +1.11 nats 且答案 40 token | **不做**（超预算） |
| E. SODA / smoltalk 等长上下文对话 | 大 | +1.8 nats | **不做** |

A 和 B 都不需要下载任何东西，`build_chat_corpus.py` 里加两种 prompt 就能出。

## 五、两个"别做"的判断

**1. 别让模型产出给定词表。** CE 4.66 / ppl 106，远高于任何语料。原因不是模型笨，
是**这个任务本身没有信息**：问"该用哪些词"，答案是随机的三选一，模型能学到的只有
词表分布，学不到对应关系。现有语料里 `Write a story using these words: a, b, c`
是把词放在 **prompt** 里、答案里自然出现 —— 那个是对的，别改成反过来。

**2. 别用加语料的方式解决事实题。** 三条证据：
- 我们模型 117 万参数；FineWeb 实测 CE 5.20、Cosmopedia 6.09，差 2.4 nats = 从头训。
- HF 微模型里参数最多的 Nano（9.97M，300 亿 token）照样答不了事实题。
- 固件已经有 20 条意图规则，`i feel sad today`、`what is your name` 这类问题
  本来就是规则在答（板上验收里被正确识别并排除）。

事实题的正确解法是**扩规则**，不是扩语料。语料只管"怎么接话"。

## 六、怎么在 10 分钟内验证任何新候选

不用下载整个数据集，也不用改训练。三步：

```bash
# 1) 把候选整理成 "User: ...\nBot: ..." 两行一条（或直接是纯文本）
# 2) 量它
cd espllm && THREADS=4 python eval_corpus_table.py model/model_mixed4_128.pt.best \
    candidate=E:/espllm_data/corpus_probe/kind_candidate.txt --limit=60000
# 3) 看两列：fits（能不能装进窗口）、答案 CE（比 control 2.40 高多少）
```

判据：**fits < 50% 直接否**（上下文结构不匹配，调不回来）；答案 CE 比 control 高
0.5 nats 以内可以考虑，高 1 nat 以上就别加 —— 那等于让 117 万参数同时学两种语言。

辅助脚本：
- `convert_soda.py` —— 把 parquet 式的多轮对话转成 (prompt, answer)，示范怎么接
- `probe_dialogue_supply.py` —— 统计某个语料里可提取的对话供给量
- `probe_soda_len.py` —— 量上下文/答案长度分布，先判断"装不装得下"
